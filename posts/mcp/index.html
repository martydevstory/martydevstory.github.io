1. MCP (Model Context Protocol) 소개

MCP는 애플리케이션이 LLM에 컨텍스트를 제공하는 방식을 표준화하는 개방형 프로토콜입니다.

기존에 도구 호출(Tool Calling)을 통해 비슷한 기능을 제공했습니다. 그러면 도구 호출과 차이는 무엇일까요?

MCP는 AI 애플리케이션을 위한 USB-C 포트와 같습니다. USB-C가 다양한 주변 기기와 액세서리에 기기를 연결하는 표준화된 방식을 제공하는 것처럼, MCP는 AI 모델을 다양한 데이터 소스 및 도구에 연결하는 표준화된 방식을 제공합니다.

왜 MCP인가?

MCP는 LLM을 기반으로 에이전트와 복잡한 워크플로를 구축하는 데 도움을 줍니다. LLM은 데이터 및 도구와 통합해야 하는 경우가 많으며, MCP는 다음과 같은 기능을 제공합니다.

  • LLM이 직접 연결할 수 있는 미리 구축된 통합 목록이 점점 증가
  • LLM 공급자와 벤더 간 전환의 유연성
  • 인프라 내에서 데이터를 보호하기 위한 모범 사례

MCP 범용 아키텍처

2. MCP 핵심 아키텍처 살펴보기

2. 1. 클라이언트-서버 아키텍처

MCP는 클라이언트-서버 아키텍처를 구조입니다.

  • 호스트 : 연결을 시작하는 Claude Desktop 또는 IDE와 같은 LLM 애플리케이션을 말합니다.
  • 클라이언트 : 호스트 애플리케이션 내부에서 서버와 1:1 연결을 유지합니다.
  • 서버 : 클라이언트에게 컨텍스트, 도구 및 프롬프트를 제공합니다

2. 2. 핵심 구성 요소

  • 프로토콜 계층 : MCP 메시지와 명령을 정의합니다.
  • 전송 계층 : 클라이언트-서버 간의 데이터 전송 방식으로 로컬 프로세스에 이상적인 stdio와 스트리밍을 위한 스트리밍 HTTP 사용합니다.
  • 메시지 유형 : 클라이언트와 서버가 주고받는 요청(request), 결과(result), 오류(error), 알림(notification) 데이터 형식을 정의합니다.

2. 3. 연결 수명 주기 (LifeCycle)

  • 초기화 (Initialization) : 클라이언트는 버전과 기능을 요청하면 서버에서 응답 후 클라이언트로 확인 보냄
  • 메시지 교환 (Message Exchange) : 요청과 응답 및 일방적인 알림을 통해 실제로 데이터를 주고받는 단계
  • 종료 (Termination) : 통신이 끝났을 때 연결 종료

3. 주요 개념

MCP에서 다루는 주요 개념인 리소스, 프롬프트, 도구, 샘플링, 루트, 전송에 대해서 알아보겠습니다.

3. 1. 리소스 (Resources)

리소스는 서버의 데이터와 콘텐츠를 LLM이 사용할 수 있고 MCP 서버가 클라이언트에게 제공하려는 모든 종류의 데이터를 나타냅니다.

리소스가 제공하는 데이터는 파일 콘텐츠, 데이터베이스 레코드, API 응답, 라이브 시스템 데이터, 스크린숏 및 이미지, 로그 파일 등이 있습니다.

각 리소스는 고유한 URI로 식별되며 텍스트 또는 이진 데이터를 포함할 수 있습니다.

1
2
3
4
5
6
7

# 형식
[protocol]://[host]/[path]

# 예
file:///home/user/documents/report.pdf
postgres://database/customers/schema
screen://localhost/display1

3. 1. 2. 리소스 유형

리소스는 텍스트와 바이너리 두 가지 유형의 콘텐츠가 포함됩니다.

텍스트는 UTF-8로 인코딩 된 텍스트 데이터로 소스코드, 구성 파일, 로그 파일, JSON/XML 데이터, 일반 텍스트 용도로 적합하고

바이너리는 base64로 인코딩된 원시 바이너리 데이터로 이미지, PDF, 오디오/비디오 파일, 텍스트 형식이 아닌 용도에 적합합니다.

3. 1. 3. 리소스 탐색

리소스 탐색에서 직접 또는 리소스 템플릿을 통해 사용 가능한 리소스를 찾을 수 있습니다.

3. 1. 5. 리소스 업데이트

MCP는 목록과 콘텐츠가 업데이트되면 nofifications/resources/list_changed 알림을 통해 클라이언트에게 알릴 수 있습니다.

특정 콘텐츠 업데이트가 되면 다음과 같은 순서로 구독 및 구독 취소가 가능합니다.

  1. 클라이언트가 resources/subscribe리소스 URI와 함께 전송
  2. notifications/resources/updated리소스가 변경되면 서버가 전송
  3. resources/read로 클라이언트는 최신 콘텐츠를 가져옴
  4. resources/unsubscribe로 클라이언트는 구독 취소 가능

const server = new Server({
  name: "example-server",
  version: "1.0.0"
}, {
  capabilities: {
    resources: {}
  }
});

// 사용 가능한 리소스 목록 조회
server.setRequestHandler(ListResourcesRequestSchema, async () => {
  return {
    resources: [
      {
        uri: "file:///logs/app.log",
        name: "Application Logs",
        mimeType: "text/plain"
      }
    ]
  };
});

// 리소스 내용 읽기
server.setRequestHandler(ReadResourceRequestSchema, async (request) => {
  const uri = request.params.uri;

  if (uri === "file:///logs/app.log") {
    const logContents = await readLogFile();
    return {
      contents: [
        {
          uri,
          mimeType: "text/plain",
          text: logContents
        }
      ]
    };
  }

  throw new Error("Resource not found");
});

3. 2. 프롬프트 (Prompts)

3. 2. 1. 재사용할 수 있는 프롬프트 템플릿 및 워크플로 만들기

매번 새롭게 프롬프트를 작성할 필요 없이 자주 쓰는 프롬프트와 워크플로를 서버에 미리 저장해 놓고 클라이언트가 이를 쉽게 불러와 사용자나 LLM에 전달할 수 있습니다.

이렇게 하면 공통으로 반복되는 LLM과의 상호작용 방식을 표준화하고 쉽게 공유할 수 있어 효율적입니다.

미리 정의된 프롬프트를 통해 수행할 수 있는 항목들이 다음과 같습니다.

동적 인수 허용

예를 들어 사용자가 입력한 위치나 날짜에 따라 프롬프트가 바뀌도록 구성이 가능합니다.

1
2
3
4

{
  "template": "What is the weather in {location} on {date}?",
  "input_variables": ["location", "date"]
}

리소스 컨텍스트 포함

프롬프트 생성 시, 입력 외에 MCP 리소스에 포함된 문서, 툴 설명, 메모리와 같은 데이터를 자동으로 포함할 수 있습니다.

1
2

{
  "template": "Using the following documentation: {doc_context}, answer the question: {user_input}",
  "input_variables": ["doc_context", "user_input"]
}

다수 상호 작용 연결

하나의 프롬프트에서 끝나는 것이 아니라, 이전 대화의 맥락이나 사용자 선택에 따라 이어지는 프롬프트 시퀀스를 구성할 수 있습니다.

MCP에서는 프롬프트들을 그래프 노드처럼 연결하여 LLM 워크플로 구성이 가능합니다.

다음 예는 작업에 대한 알림을 설정하는 다수 프롬프트 연결입니다.

1
2
3

1. "어떤 작업에 도움을 원하시나요?" -> 사용자 응답: "알림 설정"
2. 다음: "몇 시로 설정해야 하나요?" -> 사용자 응답: "내일 오전 10시"
3. 최종: "내일 오전 10시에 알림을 설정합니다."

특정 워크플로 가이드

프롬프트가 단순한 질문으로 끝나는 것이 아니라 사용자를 특정 절차나 워크플로를 따르도록 유도하여 프롬프트를 자동화합니다.

예를 들어 사용자가 여행 계획을 세울 수 있도록 단계별 질문을 던지는 프롬프트 만듭니다.

2. 어떤 날짜로 계획하고 계신가요?
3. 호텔 추천이 필요하신가요?

3. 3. 도구 (Tools)

MCP에서 도구는 서버가 실행할 수 있는 기능을 외부에 노출할 수 있도록 해주며, 클라이언트가 이를 호출하고 LLM이 작업 수행을 위해 사용할 수 있도록 합니다.

도구의 주요 특징은 다음과 같습니다:

  • 탐색(Discovery) : 클라이언트는 tools/list 요청을 보내 사용할 수 있는 도구 목록을 확인
  • 호출(Invocation) : tools/call 요청을 통해 도구를 호출하면, 서버는 해당 작업을 수행하고 결과를 반환
  • 유연성(Flexibility) : 도구는 단순한 계산부터 복잡한 API 연동까지 다양함

리소스와 마찬가지로, 도구는 고유한 이름으로 식별되며, 사용법을 안내하는 설명도 포함할 수 있습니다.

그러나 리소스와 다른 점은, 도구는 상태를 변경하거나 외부 시스템과 상호작용을 하는 동적인 기능을 수행합니다.

    openWorldHint?: boolean;   // true면 도구가 외부 시스템과 상호작용함
  }
}

  name: "example-server",
  version: "1.0.0"
}, {
  capabilities: {
    tools: {}
  }

// 사용가능한 도구 정의
server.setRequestHandler(ListToolsRequestSchema, async () => {
  return {
    tools: [{
      name: "calculate_sum",
      description: "Add two numbers together",
      inputSchema: {
        type: "object",
        properties: {
          a: { type: "number" },
          b: { type: "number" }
        },
        required: ["a", "b"]
      }
    }]
  };
});

// 도구 수행 핸들링
server.setRequestHandler(CallToolRequestSchema, async (request) => {
  if (request.params.name === "calculate_sum") {
    const { a, b } = request.params.arguments;
    return {
      content: [
        {
          type: "text",
          text: String(a + b)
        }
      ]
    };
  }
  throw new Error("Tool not found");
});

3. 4. 샘플링 (Sampling)

MCP에서의 샘플링은 서버가 직접 LLM에 프롬프트를 보내고 결과를 받을 때, 보안과 개인 정보 보호를 유지하면서 에이전트 수행을 가능하게 하는 메커니즘입니다. 즉, 서버가 사용자의 승인 없이 임의로 민감한 데이터를 LLM에 보내지 못하도록 합니다.

MCP의 샘플링과 데이터 분석에서 사용하는 데이터 샘플링은 다릅니다. 데이터 분석에서 샘플링은 통계적 추정을 위해 실제 데이터를 일정 방법으로 선택하는 과정입니다.

3. 4. 1. 샘플링 작동 방식

샘플링 흐름은 다음과 같습니다.

  1. 서버가 클라이언트에 sampling/createMessage 요청 전송
  2. 클라이언트는 LLM에 프롬프트와 파라미터를 사용해 completion을 요청
  3. 클라이언트는 LLM의 completion 수신
  4. 클라이언트가 응답 텍스트의 민감한 데이터 제거, 길이 조정 및 승인 절차 등 원하는 방식으로 검토하고 수정
  5. 클라이언트가 최종 결과를 서버에 반환

샘플링은 휴먼-인-더-루프 디자인으로, 사용자가 프롬프트와 응답을 모두 제어할 수 있습니다.

Completion은 “채우기”라는 뜻 그대로, LLM이 주어진 프롬프트에 이어서 생성해 주는 텍스트를 가리킵니다.

예를 들어 프롬프트가 “Hello, how are you?” 라면, completion은 “ I’m fine, thanks for asking!” 같은 뒤이은 응답 텍스트가 됩니다.

3. 4. 3. 요청 파라미터

메시지 (Messages)

messages 배열은 LLM에 보낼 대화 히스토리를 포함합니다. 각 메시지는 다음과 같은 구조를 가집니다:

  • role: "user" 또는 "assistant"
  • content: 메시지 내용으로 텍스트 또는 이미지
    • 텍스트 : text 필드로 전달됨
    • 이미지 : data(base64)와 mimeType 필드를 포함

모델 선호 설정

modelPreferences 객체는 서버가 모델 선택에 대한 선호도를 지정할 수 있습니다 :

  • hints: 클라이언트가 적절한 모델을 선택할 수 있도록 제공하는 모델 이름 제안 배열
    • name: 전체 또는 부분 모델 이름을 나타내는 문자열 (예: "claude-3", "sonnet")
    • 클라이언트는 이 힌트를 바탕으로 다른 공급자의 동등한 모델로 매핑할 수 있음
    • 여러 개의 힌트는 우선순위로 평가
  • 우선순위 값 (0~1 사이의 정규화된 값):
    • costPriority: 비용 최소화 중요
    • speedPriority: 지연 시간 응답 중요
    • intelligencePriority: 고성능 모델 사용 중요

클라이언트가 최종 모델 선택 결정권을 가집니다

시스템 프롬프트

선택적으로 systemPrompt 필드를 사용하여 특정 시스템 프롬프트를 요청할 수 있습니다.

클라이언트는 이를 수정하거나 무시할 수 있습니다.

컨텍스트 포함 설정

includeContext 파라미터는 어떤 MCP 컨텍스트를 포함할지를 지정합니다:

  • "none": 아무 컨텍스트도 포함하지 않음
  • "thisServer": 요청한 서버의 컨텍스트만 포함
  • "allServers": 모든 연결된 MCP 서버의 컨텍스트 포함

실제 포함되는 컨텍스트는 클라이언트가 결정합니다.

샘플링 파라미터

LLM 응답 생성을 미세 조정할 수 있는 파라미터:

  • temperature: 무작위성 제어 (0.0 ~ 1.0)
  • maxTokens: 생성할 최대 토큰 수
  • stopSequences: 생성을 멈출 문자열 배열
  • metadata: 공급자별 추가 파라미터

3. 5. 루트 (Roots)

루트는 MCP에서 서버가 작업할 수 있는 경계(boundary)를 정의하는 개념으로 클라이언트가 서버에게 관련된 리소스와 그 위치를 알려주는 방법을 제공합니다.

3. 5. 1. 루트란 무엇인가

루트는 클라이언트가 서버에게 '여기를 중심으로 작업해 주세요'라고 제안하는 URI입니다.

클라이언트가 서버에 연결할 때, 서버가 어떤 루트를 기준으로 동작할지 지정합니다.

루트는 주로 파일 시스템 경로에 쓰이지만, HTTP URL을 포함한 모든 유효한 URI를 사용할 수 있습니다.

1
2
3

# 루트 예
file:///home/user/projects/myapp  
https://api.example.com/v1

3. 5. 2. 루트를 사용하는 이유

루트는 다음과 같은 중요한 목적을 가집니다:

  • 안내(Guidance) : 서버에게 관련 리소스 및 위치를 알려줍니다.
  • 명확성(Clarity) : 어떤 리소스가 워크스페이스에 포함되어 있는지 명확하게 합니다.
  • 조직화(Organization) : 여러 루트를 통해 다양한 리소스를 동시에 다룰 수 있습니다.

3. 5. 3. 루트가 작동하는 방식

클라이언트가 루트를 지원하는 경우 다음을 수행합니다 :

  1. 연결 시 루트 기능을 선언합니다.
  2. 서버에게 적용할 루트 목록을 전달합니다.
  3. (지원하는 경우) 루트가 변경되면, 서버에게 알립니다.

루트 정보는 강제력이 없는 참고용이지만, 서버는 다음을 지켜야 합니다:

  • 전달받은 루트를 존중(respect)해야 합니다.
  • 루트 URI를 기반으로 리소스를 탐색하고 접근해야 합니다.
  • 루트 경계 내에서 작업을 우선 처리해야 합니다.

3. 5. 4. 일반적인 사용 사례

루트는 다음과 같은 경계를 정의하는 데 주로 사용됩니다:

  • 프로젝트 디렉토리
  • 저장소(Repository) 위치
  • API 엔드포인트
  • 설정(Configuration) 위치
  • 리소스 범위(Boundaries)

3. 6. 전송 (Transport)

MCP에서 전송은 클라이언트와 서버 간 통신의 주축을 담당하고 메시지가 어떻게 전송되고 수신되는지에 대한 기본 메커니즘을 처리합니다.

3. 6. 1. 메시지 형식

표준 입출력 (stdio)

stdio를 사용하면 좋은 경우:

  • 커맨드라인 도구를 개발할 때
  • 로컬 통합 기능을 구현할 때
  • 간단한 프로세스 간 통신이 필요할 때
  • 셸 스크립트와 연동할 때

스트리밍 HTTP 전송은 클라이언트에서 서버 통신에 HTTP POST 요청을 사용하고, 서버에서 클라이언트 통신에는 선택적인 Server-Sent Events(SSE) 스트림을 활용합니다.

스트리밍 HTTP를 사용하면 좋은 경우:

  • 웹 기반 통합을 구축할 때
  • HTTP를 통한 클라이언트-서버 통신이 필요할 때
  • 상태를 유지하는 세션을 운영해야 할 때
  • 여러 클라이언트를 동시에 지원할 때
  • 연결 재개(resumeable)가 필요할 때

동작 방식

동작 방식은 클라이언트가 서버로 보내는 모든 JSON-RPC 메시지는 MCP 엔드포인트에 새로운 HTTP POST 요청으로 전송됩니다.

서버는 다음 두 가지 방식 중 하나로 응답할 수 있습니다:

  • 단일 JSON 응답 (Content-Type: application/json)
  • 여러 메시지를 전송하는 SSE 스트림 (Content-Type: text/event-stream)

서버는 클라이언트에게 요청이나 알림을 다음과 같이 보낼 수 있습니다:

  • 클라이언트 요청으로 열려 있는 SSE 스트림
  • MCP 엔드포인트에 대한 HTTP GET 요청으로 생성된 SSE 스트림

세션 관리

스트리밍 HTTP는 여러 요청에 걸쳐 컨텍스트를 유지하기 위해 상태 저장 세션을 지원합니다.

  • 세션 초기화 : 서버는 초기화 과정에서 Mcp-Session-Id 헤더를 통해 세션 ID를 할당할 수 있습니다.
  • 세션 유지 : 클라이언트는 이후 모든 요청에 Mcp-Session-Id 헤더로 세션 ID를 포함해야 합니다.
  • 세션 종료 : 세션을 종료하려면 HTTP DELETE 요청에 세션 ID를 담아 명시적으로 종료할 수 있습니다.

재연결 및 재전송 지원

끊어진 연결을 다시 이어가기 위해 스트리밍 HTTP는 다음 기능을 제공합니다:

  • 이벤트 ID : 서버가 각 SSE 이벤트에 고유 ID를 붙여 추적할 수 있습니다.
  • 마지막 이벤트부터 재개 : 클라이언트는 Last-Event-ID 헤더를 보내 끊긴 지점 이후부터 다시 수신을 시작합니다.
  • 메시지 재전송 : 서버가 연결 끊긴 지점 이후 놓친 메시지를 다시 보내 줍니다.

이를 통해 불안정한 네트워크 환경에서도 안정적인 메시지 전달을 보장할 수 있습니다.

보안 고려 사항

스트리밍 HTTP 전송을 구현할 때는 다음 보안 모범 사례를 검토합니다:

  • Origin 헤더 검증 : 모든 수신 연결에서 Origin 헤더를 검증해 DNS 리바인딩 공격을 방지합니다.
  • 로컬호스트 바인딩 : 로컬 환경에서는 모든 인터페이스(0.0.0.0)가 아니라 localhost(127.0.0.1)에만 바인딩합니다.
  • 인증 구현 : 모든 연결에 대해 적절한 인증 절차를 적용합니다.
  • HTTPS 사용 : 실제 운영 환경에서는 반드시 TLS/HTTPS를 사용합니다.
  • 세션 ID 검증 : 세션 ID가 충분히 암호화되어 있고, 올바르게 검증되도록 합니다.

이러한 보호 조치가 없으면 공격자는 DNS 리바인딩 기법을 이용해 원격 웹사이트에서 로컬 MCP 서버와 상호작용할 수 있습니다.

3. 6. 3. 사용자 지정 전송 (Custom Transports)

MCP는 특정 요구사항에 맞춰 사용자 지정 전송을 손쉽게 구현할 수 있도록 지원합니다. 모든 전송 구현은 Transport 인터페이스를 준수하시면 됩니다.

사용자 지정 전송을 적용할 수 있는 사례:

  • 자체 네트워크 프로토콜
  • 특수화된 통신 채널
  • 기존 시스템과의 통합
  • 성능 최적화

interface Transport {

  • 프로토콜 오류
  • 네트워크 타임아웃

정리

MCP는 LLM 애플리케이션에 컨텍스트와 도구, 데이터 소스를 표준화된 방식으로 연결해 주는 “AI용 USB-C 포트” 같은 프로토콜입니다.

클라이언트-서버 아키텍처를 기반으로, IDE와 같은 호스트, 클라이언트 및 서버로 구성되며, 프로토콜·전송·메시지 계층을 통해 안정적인 통신을 보장합니다.

초기화, 메시지 교환 및 종료의 연결 수명 주기와 요청, 전송 및 프로토콜 수준의 JSON-RPC 표준 에러 처리 방식을 지원해 복잡한 워크플로도 일관되게 관리할 수 있습니다.

또한 MCP의 주요 개념으로는 파일, 이미지, API 및 DB처럼 다양한 데이터를 제공하는 리소스, 재 사용할 수 있는 템플릿과 워크플로의 프롬프트, 실행할 수 있는 기능을 노출하고 호출을 할 수 있는 도구, 휴먼-인-더-루프 방식으로 서버가 사용자 승인을 통해 수행할 수 있는 샘플링, 서버가 작업할 수 있는 경계 지정을 하는 루트, stdio와 스트리밍 HTTP의 표준 메커니즘을 제공하는 전송이 있습니다.

MCP를 도입하면 다양한 데이터 소스와 서드파티 툴을 LLM에 쉽게 연결해 복합적인 자동화 파이프라인을 구축할 수 있으며, 벤더 변경이나 보안 요건 변경에도 유연하게 대처할 수 있습니다.
